1. 概要

Harden Runner（step-security/harden-runner）は、GitHub ActionsのCI/CDランナー上で ネットワーク通信・ファイル操作・プロセス活動をリアルタイム監視するセキュリティエージェントです。 StepSecurityが開発し、週間2,500万以上のCI/CD実行を保護しています。

Microsoft・Google・Kubernetesなど11,000以上のプロジェクトに採用されており、 tj-actions/changed-files侵害（CVE-2025-30066）やaxios npmパッケージ侵害など、 実際のサプライチェーン攻撃の検知実績があります。

主な機能

機能説明
ネットワーク監視DNS・L3/L4・L7(HTTPS)レベルで通信先を可視化
egress-policy: audit通信を記録するだけ。ブロックしない
egress-policy: block許可リスト外の通信を遮断
ベースライン比較過去の通信パターンと比較し異常を検知
グローバルIOCリスト既知の悪意あるドメイン/IPを全顧客共有でブロック
プロセス監視逆シェルやメモリ読み取りなどの攻撃技法を検知

2. 動作アーキテクチャ

Harden Runnerは「外部リポジトリを能動的に監視する」ものではありません。 自分のCIランナー上に eBPFエージェントを仕込み、そのランナー上で起きていることを監視する設計です。

GitHub Actions Runner (ubuntu-latest) ├─ eBPF エージェント（Harden Runnerが起動時にインストール） │ ├─ DNS クエリを全捕捉 │ ├─ L3/L4 ネットワーク通信を監視 │ └─ L7 HTTPS の宛先・内容も可視化 │ ├─ StepSecurity クラウドバックエンド │ ├─ ベースライン蓄積・比較 │ ├─ 異常検知アラート │ └─ ダッシュボード可視化 │ └─ ローカル実行（クラウド不要） ├─ egress-policy: block によるリアルタイム遮断 └─ グローバルIOCリストによる既知脅威ブロック

Harden Runnerのステップが実行されると、まずStepSecurityのAPIに対してmonitorリクエストを送信し、 許可を得た場合にのみeBPFエージェントがランナーにインストールされます。

3. 検知の仕組み

過去の実際のインシデント（tj-actions侵害、axios侵害など）がどのように検知されたかを整理します。

検知レイヤー

レイヤー仕組み有効モード
ベースライン比較 過去のrunから「通常の通信先」を学習。初めて現れるドメインへの通信を異常とみなす audit block
グローバルIOCリスト StepSecurity SOCが管理する既知悪意ドメイン/IPのリスト。全顧客共有 audit block
プロセス監視 逆シェル・メモリ読み取りなどの攻撃技法をカーネルレベルで検知 block
HTTPS可視化 L7レベルでAPI呼び出しの詳細を監視。トークン悪用を検出 audit block
重要：auditモードでも検知は機能する ブロックはしないが、ベースライン逸脱（未知ドメインへの初回通信）は auditモードでも検知・記録されます。サプライチェーン攻撃の多くは 「攻撃者の新規ドメインへの通信」を伴うため、auditモードでも事後分析が可能です。

なぜ外部の侵害（tj-actions等）を検知できるのか

侵害されたActionのコードがランナー上で実行される際、攻撃者サーバーへの通信が発生します。 このタイミングで「ベースラインにない新規ドメインへの通信」としてフラグが立ちます。 外部リポジトリを監視しているのではなく、自分のランナー上での実行結果として検知しています。

4. デモワークフローで確認した挙動

本リポジトリに4つのワークフローを作成し、挙動を確認しました。

ファイルモード結果確認内容
01-audit.yml audit 成功 httpbin.org等への通信がSummaryに記録される
02-block.yml block（許可リストあり） 成功 許可リスト内のnpm・github.comへの通信は通過
03-block-violation.yml block（狭い許可リスト） 成功 || echoでエラーを握り潰しているため成功扱い
04-block-fail.yml block（エラー握り潰しなし） 失敗 httpbin.orgがブロックされcurlが失敗→ワークフロー停止

blockモードの設定例

- name: Harden Runner
  uses: step-security/harden-runner@v2
  with:
    egress-policy: block
    allowed-endpoints: >
      github.com:443
      api.github.com:443
      registry.npmjs.org:443
注意：blockモードでワークフローを失敗させるには ブロックされたコマンドの終了コードをそのままステップに伝えることが必要です。 || echo "..."やcontinue-on-error: trueがあると ブロックが発生してもワークフローは成功扱いになります。

5. ライセンスとサービス構造

Harden Runnerはコードとサービスが明確に分離しています。

対象ライセンス意味
GitHubリポジトリのコード Apache 2.0 自由に閲覧・改変・再配布可能。商用利用も可
StepSecurityクラウドサービス SaaS利用規約 ダッシュボード・ベースライン・異常検知はStepSecurityのサービスとして提供

実際の制限はコードではなくAPIで制御

ソースコード（src/setup.ts）を確認したところ、 アクション起動時に必ずStepSecurityのmonitor APIを呼び出す実装になっています。 APIがHTTP 409を返した場合、エージェントのインストールをスキップする仕組みです。 

// setup.ts より抜粋
const resp = await _http.postJson(
  `${api_url}/github/${GITHUB_REPOSITORY}/actions/runs/${GITHUB_RUN_ID}/monitor`,
  monitorRequestData
);

if (String(statusCode) === "409") {
  console.log(HARDEN_RUNNER_UNAVAILABLE_MESSAGE);
  return; // エージェントインストールをスキップ
}
disable-telemetry: true を設定しても このmonitor APIへの呼び出しはスキップされません。 テレメトリの無効化とエージェント起動の許可は別の処理です。

6. プライベートリポジトリでの挙動（実測）

本リポジトリをprivateに変更しworkflow_dispatchで実行したところ、 以下の挙動が確認されました。

1
Harden Runnerステップが起動し、StepSecurity monitor APIを呼び出す
2
APIがプライベートリポジトリ＋無料プランを検知し、エラーレスポンスを返す
3
eBPFエージェントのインストールをスキップ（監視・ブロック機能は無効）
4
ステップ自体は成功扱いで終了。ワークフロー全体は通る
5
Job SummaryにHTML形式の警告が表示される

実際に表示されたSummaryの内容

⚠️ Your GitHub Actions Runtime Security is currently disabled!

It appears that you're using the Harden-Runner GitHub Action by StepSecurity within a private repository. However, runtime security is not enabled as your organization hasn't signed up for a free trial or a paid subscription yet.

To enable runtime security, start a free trial today by installing the StepSecurity Actions Security GitHub App.

「落ちる」のではなく「何もしないまま成功する」 ワークフロー自体は失敗しないため、気づかずに無防備な状態で運用してしまうリスクがあります。 プライベートリポジトリで使用する場合は、Summaryの確認が必須です。

注意点

  • ベースラインが安定しないと異常検知の精度が落ちる（依存関係のバージョンが頻繁に変わる場合など）
  • disable-telemetry: true にするとクラウド機能は無効になるが、monitor APIへの呼び出し自体は残る
  • APIコールが失敗（タイムアウト等）した場合はエージェントがそのまま起動するケースがある
  • 100人以上の開発者にはボリュームディスカウントあり

8. まとめ

Harden Runnerとは何か

CI/CDランナー上のeBPFエージェントとして動作し、外部通信・プロセス・ファイル操作を監視するEDR的なツールです。 サプライチェーン攻撃を「ランナー上での実行時の通信」として捉えることで、 外部リポジトリを能動的に監視しなくても侵害を検知できます。

利用可否の判断基準

ユースケース判断
OSSプロジェクト・個人のパブリックリポジトリ無料で利用可
社内プライベートリポジトリEnterprise契約が必要（$16/人/月）
プライベートで無料のまま使うAPIレベルで無効化される（グレーではなくNG）
セルフホストランナーEnterprise契約が必要
コードはApache 2.0、制限はサービス規約で管理 ライセンス上の制限はコードではなくStepSecurityのクラウドAPIで技術的に強制されています。 グレーな領域はなく、プライベートリポジトリでの利用はEnterprise契約が前提です。
